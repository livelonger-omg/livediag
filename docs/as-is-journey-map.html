李工 · 网格/装维工程师

主线 Persona ｜ 直播投诉处理的责任人

负责 8～15 个小区的家宽维护，日均 4～6 单，其中直播类投诉最难判、最耗时。 手上工具：手机工单 App、微信、网管/光衰查询、笔记本上的 ping / tracert、测速网站。 目标：尽快给出结论并闭环，避免二次上门和跨部门扯皮。
能力边界：懂 ping/测速，但不懂 TCP 抓包、不懂 CDN 调度， 手里没有“能证明问题在哪一段”的客观数据。

每天 4～6 单 结果导向 怕返工 要证据

02 远程初判 测速只看下行，无法判断上行能力与链路质量 把“上行”作为一等公民：码率、上行 RTT、上行丢包同屏可见 整机上行 / 推流上行 / 网关与接入跳 RTT、丢包实时看板 已实现
03 开播复现 抓不到故障现场，靠人工守点 现场零操作：程序常驻、自动识别开播并开始记录 开机自启 + 托盘常驻；自动识别推流进程（TCP 443/1935、IPv6、UDP）；会话自动开始/结束、断流自动记录 已实现
04 定界定责 无法说清“问题在哪一段” 按网络分段给出证据：本机 → 网关 → 接入网 → 推流节点 自动逐跳定位“网关之后第一跳”并持续测时延/抖动/丢包；与网关、推流节点 RTT/丢包并列对比；异常自动生成归因结论 已实现
04 定界定责 举证无力，跨专业/平台推诿 一键产出可外发的证据包 HTML 诊断报告（含曲线、KPI、结论、事件时间线）+ CSV 原始数据 + 现场连接快照 已实现
04 定界定责 识别不到推流程序时无从下手 失败也要留证据：记录当时全部连接与进程写出 “整机在上行但识别不到推流进程”事件 + data\diag 连接明细快照 已实现
05 处置验证 处置前后无对比，靠体感判断 同一会话内形成“处置前—处置后”对照 会话内质量分与曲线连续记录，处置动作可直接对照前后指标 已实现

需要与您确认的 4 个问题（决定 v2 地图是否准确）

  1. 主线角色是否正确？现在按“网格/装维工程师”作为主 persona。若实际是有线中心值班工程师远程支撑为主、装维只负责上门执行，阶段责任与触点需要重排。
  2. 流程是否缺少分支？是否需要补“派单/预约上门”“政企专线/商宽直播”“直播基地/多机位”等分支？这些场景的痛点和阶段数量会不同。
  3. 现状指标能否给真实值？表中“远程解决率 20%”“重复上门率 30%”“定界耗时 6 小时”等为估算示例，若有工单系统统计口径（如平均处理时长、一次解决率），请提供，我替换为真实数据。
  4. 是否需要 To-Be 对照版？立项评审通常需要“现状 vs 部署后”对比 + 效益测算（减少上门次数、缩短定界时长、降低重复投诉）。我可以在地图右侧加一列“部署后阶段变化”。
另外：地图中的“情绪值”为访谈式主观评分（−3 ～ +2），用于排序痛点优先级，不作为考核指标；所有标注“待核实”的数字均需以工单系统真实统计替换。
绘制方法：以真实任务流为主线，按“阶段 → 目标 → 行为 → 触点 → 想法 → 情绪 → 痛点 → 指标”逐层展开，再由痛点反推机会点与本项目能力映射；情绪曲线用于识别体验低谷（当前低谷集中在阶段 04 定界定责）。
